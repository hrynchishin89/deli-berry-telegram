# Дели Берри — Mini App v2.0

Доработка существующего `hrynchishin89/deli-berry-telegram` и `@berrymscbot` по единому ТЗ от 02.10.2026. Исходная база — `feat/cloudflare-free-d1@867d5c9`. Прежние исходники и архивы остаются в репозитории; этот каталог раскрывает и продолжает подготовленный Cloudflare runtime.

**Публичной публикации этой сборки пока нет.** Все live-флаги по умолчанию выключены. Скриншоты и результаты в пакете относятся к локальному Chromium + workerd/D1 с синтетическими данными. Яндекс Пэй sandbox, реальные сообщения Telegram, действующий HTTPS URL и входы бота требуют отдельной проверки после получения доступа.

## Что изменено

- 8 покупательских групп, 9 исходных семейств, 16 неизменённых SKU и цен. Явные оформления с совместимостью и хешем фото в `public/catalog.json`.
- Корзина хранит каждую комплектацию отдельно. Сервер рассчитывает копейки, проверяет дополнения, цену, точку, стоп-лист и время МСК с шагом 15 минут.
- В D1 сохраняется неизменяемый снимок всех строк заказа. Повтор отправки использует один ключ. Согласованная новая версия сохраняет предыдущий снимок.
- Один оператор получает все позиции, фотографии, SKU/оформления, надписи, получение и контакты. Расписание/праздники/стоп-листы меняются отдельно для каждой точки без сборки.
- Подготовлена интеграция Яндекс Пэй: ES256, сырое тело `/v1/webhook`, JWKS, проверка продавца/суммы/валюты, смысловая дедупликация, один платёжный сценарий. Ручного PAID/REFUNDED нет.

## Запуск и проверки

Node.js 24, бесплатные Wrangler/Miniflare/Playwright; зависимости закреплены в lock-файле.

```sh
cd cloudflare
npm ci
npm run check
npx playwright install chromium
node scripts/qa-server.mjs
```

В другом терминале, из `cloudflare`:

```sh
node scripts/browser-qa.mjs
node scripts/restore-check.mjs
```

QA-сервер слушает только `127.0.0.1:8787`, создаёт временную D1, использует фиктивный токен, отключает Telegram и оплату. Browser QA подставляет подписанные **синтетические** идентичности 100/900. Это не проверка реальной авторизации в контейнере Telegram. `QA_PREVIEW=true node scripts/qa-server.mjs` проверяет витрину без приёма контактов. Не вводить реальные данные в QA.

Обычный локальный preview с выключенными заказами:

```sh
npm run migrate:local
npm run dev
```

`npm run check`: сохранность исходных фотографий и медиареестра, тесты на native D1/клиенте, dry-run сборки Worker. `browser-qa.mjs`: мобильные размеры, desktop, увеличение текста, изолированная заявка, оператор и согласование. `restore-check.mjs`: миграции → синтетический заказ → реальный локальный SQL-экспорт → новая локальная D1 → сравнение снимка, суммы, событий и точек. Результаты сохраняются в `evidence/`.

## Данные и совместимость

`public/catalog.json` — единственный runtime-источник групп, семейства, SKU, фото и цен. `catalog-data.js` сохранён как совместимая статическая копия; новый клиент его не использует. Старые `product.id`/`variant.id` принимаются API, старые записи без `items` читаются адаптером одной позиции. Новый API: `items[{sku,appearanceId,quantity,addOns,inscriptionText}]` + `expectedTotalKopecks`.

Реальные заказы не переносились, не удалялись и не читались. Идентификаторы SKU не менялись. D1 миграции 0001–0003 сохранены, разрушительных миграций нет. Стоп-лист проверяется по каждой позиции при создании, подтверждении и запросе оплаты.

Неидентифицированные изображения: **C04** и прежнее **assets/set-09.webp** — цельные ягоды на фото не привязаны владельцем к базовой цене. Их не показываем отдельным покупательским выбором. Подтверждённый B04 даёт доступ к обоим SKU из 9 ягод. SET-25 восстановлен из исходного WebP; белая коробка на референсе раскрыта, выдача — в крафтовой. Фотографии не генерировались и не перекрашивались.

## Что нужно для размещения витрины

Одна внешняя блокировка публикации: авторизация **Cloudflare владельца** для существующего направления Workers Free + D1 + Static Assets. Проверка CLI: `You are not authenticated. Please run wrangler login.` В конфигурации пока нулевой UUID D1.

Для локального управляемого deploy — авторизация `wrangler login`. Для существующего GitHub Actions workflow — `CLOUDFLARE_API_TOKEN` с Workers Scripts Edit / D1 Edit и `CLOUDFLARE_ACCOUNT_ID` в Secrets; `CLOUDFLARE_D1_DATABASE_ID` и явно разрешённый `CLOUDFLARE_DEPLOY_ENABLED=true` в Variables. Значения не передавать в переписке/исходниках. Использовать аккаунт Free без привязки платных услуг; перед созданием ресурсов проверить текущие лимиты аккаунта.

Workflow читает исходники из `cloudflare/`, сначала запускает check. Deploy запускается только при заданном gate и сохраняет приём заказов/Telegram/оплату выключенными. Перед первым применением подтвердить целевой Worker и D1: **не затирать настройки реально работающего сервиса с незавершёнными заказами/оплатами**.

Порядок после предоставления доступа:

1. Зафиксировать текущий commit и приватную копию настроек. Если есть действующая БД, сделать резерв в разрешённом владельцем контуре; не добавлять его в Git/CI-артефакты. Для размещённой D1: `npx wrangler d1 export DB --remote --output /private/path/backup.sql`. Не запускать экспорт/перенос реальных контактов без выполнения требований к персональным данным.
2. Привязать UUID **существующей** D1 или создать её только если ещё нет. Применить миграции без очистки и опубликовать preview:

```sh
npm run migrate:remote
npm run deploy -- --var BUILD_COMMIT:<полный_commit>
```

3. Проверить фактический выданный HTTPS URL, `/api/health` (commit/version), каталог, assets, выключенный сбор контактов. Не выдавать локальный URL/PR за опубликованный магазин.
4. После изолированного теста — обновить доступные Main App, профиль, меню «Открыть приложение» и старые редактируемые входы `@berrymscbot`. Проверить открытие из Telegram и отображаемое имя «Дели Берри».
5. Только после проверки новой версии выключить старый checkout/перенаправить доступные старые URL. Сохранить историю и обработчики старых незавершённых заказов/платежей. Недоступные сообщения перечислить; пересланные копии удалёнными не считать.

## Заказы и персональные данные

До реального приёма нужны действующие `TELEGRAM_BOT_TOKEN`, единственный `TELEGRAM_OPERATOR_ID`, согласованная обработка/размещение персональных данных, окончательные документы и техкарты состава/аллергенов. Требуемые gates: `OWNER_LIVE_APPROVED`, `LEGAL_APPROVED`, `PERSONAL_DATA_APPROVED`, `CATALOG_LABELING_APPROVED`, затем `ORDERS_ENABLED`. Флаг — запись уже принятого решения, а не способ обойти неподтверждённые условия.

Публичный preview не показывает форму контактов. Для реальных заказов не использовать синтетический режим: он работает только на localhost/example.test. API проверяет Telegram HMAC/auth_date, права одного оператора и принадлежность заказа. Персональные ответы `no-store`; raw initData не сохраняется в черновике. Черновик живёт до 30 минут и очищается после подтверждённой отправки. Это срок локального черновика, не резерв товара или штрафной срок заявки.

## Яндекс Пэй и уведомления

Действующие имена: `YANDEX_PAY_MERCHANT_ID`, `YANDEX_PAY_API_KEY`, `PAYMENT_MODE=disabled|sandbox|production`. Callback Base URL — корень HTTPS приложения **без** `/v1/webhook`; Яндекс дописывает путь. `YANDEX_PAY_WEBHOOK_SECRET` не применяется: подпись ES256 проверяется по JWKS выбранной среды.

Sandbox пока NOT TESTED: нужны доступ/ключи существующей организации. Контрольный прогон: создание/повтор, отказ/отмена, подписанный CAPTURED, подмены, повтор с новым JWT, поздний платёж и возврат. Локальные подставные ответы этого не заменяют.

Просроченная ссылка не показывается для оплаты. Перед повторной отправкой сервер проверяет прежний платёж; автоматического нового списания нет. Закрытие/продление оплачиваемого сценария требует подтверждённого процесса провайдера. Изменения после открытия оплаты блокируются. При позднем CAPTURED отменённый заказ переходит в исключение возврата, не в производство.

Боевой режим дополнительно требует `LIVE_PAYMENTS_APPROVED`, подтверждённой кассовой схемы и реальных настроек фискализации. Текущий шлюз боевого режима ограничен поддержанной в коде схемой `FISCAL_MODE=yandex`; если у продавца другая касса, интеграцию надо адаптировать по её фактическим данным. НДС не подставлять наугад. Нет ручного подтверждения возврата; фактический возврат — через кабинет продавца и проверенное уведомление.

Telegram: `TELEGRAM_WEBHOOK_SECRET` — независимая проверка webhook самого Telegram. Outbox хранится в D1, сбои/попытки видны оператору, cron повторяет отправку. Недоставка сообщения не теряет заказ. Доставка реальному оператору/клиенту в этой среде не проверялась.

## Ограничения и откат

Workers/D1 Free имеют квоты CPU, запросов, subrequests, строк чтения/записи и хранения. Тестируется лимит SQL-запросов одного вызова сервиса; это не доказательство CPU/нагрузки в production. Нет новых подписок, домена, карты, реальных списаний или автоматического перехода на платный тариф. Персональные request logs в конфигурации выключены.

Перед откатом сохранить текущие данные/настройки и версии. Если v2 ещё не принимала заказы, можно вернуть предыдущую проверенную публикацию и входы. Если есть заказы v2, **не откатывать API к однопозиционной обработке**: выключить новый checkout, сохранить v2 API/историю/webhook и завершить активные сценарии. D1 не очищать; восстановление в отдельную БД допустимо только после проверки снимка и разрешённого контура данных. Для rehearsal используется отдельная временная локальная база, не production.
