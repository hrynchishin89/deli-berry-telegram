Версия 2.0 · 02.10.2026 · Объект: существующий бот `@berrymscbot` и его текущий репозиторий.

**Это единственное актуальное ТЗ на доработки. Оно заменяет предыдущие задания и дополнения в части требований ниже. Старые исходники, фотографии и заказы сохраняются. Новые прямые решения владельца имеют приоритет.**

## 0. Результат и порядок работы
Довести существующее приложение: **Наборы/Букеты → размер → тип клубники → фото оформления → корзина → получение → подтверждение единым оператором → Яндекс Пэй → статусы**. Не создавать новый бот, репозиторий, дизайн с нуля или параллельный каталог.

Один раз установить фактические рабочие ветку, frontend, backend и URL; известный прежний адрес `https://hrynchishin89.github.io/deli-berry-telegram/` — только ориентир, не доказательство текущей публикации. Затем изменять нужные файлы, проводить целевые проверки и собирать результат. Не повторять широкий аудит, историю и выбор хостинга при каждой правке. После неудачи менять подход только при новых данных; при внешнем блокере завершить независимые правки и запросить один конкретный недостающий доступ. Документацию открывать точечно, когда она нужна для реализации.

Без платных сервисов, TinyFish, подписок, покупки домена, привязки карты и реальных списаний. Тестовые заказы — только изолированные, без запуска производства/курьера и без настоящих данных покупателей. Публикация исправленной витрины и замена старых входов ранее разрешены владельцем; выполнять после проверки и с резервом. Это не разрешение включить боевую оплату или проводить реальный платёж.

## 4. Фото оформлений и сохранение выбора
Использовать имеющиеся согласованные assets и медиареестр. Внутри каждого размера вывести **все подтверждённые фото разных оформлений**, а не только общее фото семейства. Несколько ракурсов одного изделия — галерея одного оформления, не новые варианты покупки. Количество фотографий не обязано равняться 16.

Связь данных: `group → family → SKU + appearanceId → подтверждённые фото/подпись/совместимость`. Существующие ID и API сохраняются; добавить минимальный слой группировки/оформления. У каждого оформления зафиксировать источник фото, разрешённые SKU, реальную упаковку, включённый декор. Несколько подтверждённых расцветок могут ссылаться на один SKU; это не создаёт новую цену. Не строить автоматически произведение «все цвета × все типы × все размеры».

Карточка оформления: **фото → название/размер → подпись оформления → тип → готовность → точная цена → «Выбрать»**. Внутри одного размера общий заголовок можно не дублировать в каждой миниатюре. Выбранное состояние — рамка + отметка, не один цвет. Фото/подпись/дополнения/цена обновляются согласованно. При добавлении сохранять конкретные SKU и appearanceId; в заказе — снимок названия, комплектации, изображения/версии, цены и текста надписи. Оператор и покупатель видят тот же выбор.

Нельзя генерировать/перекрашивать товары, брать товарные фото из скриншотов интерфейса, добавлять ягоды/декор или считать каждую старую обработанную картинку одобренной. Сверять число ягод, упаковку, начинку и включённые дополнения. «Пример оформления» не оправдывает неверный состав или стоимость. Если используется референс другой начинки, обозначить именно референс оформления.

**SET-25:** восстановить ранее переданное `assets/set-25.webp` вместо заглушки «25», цену 2790 ₽ сохранить; товар выдаётся в крафтовой коробке. Если сохранённое фото показывает белую: «На фото пример оформления. Заказ выдаётся в крафтовой коробке». Не перекрашивать коробку автоматически. Если файл недоступен, не изобретать фото: локальный блокер и продолжение остальных работ.

Для A06 и базовых 9/12/16 отдельно исключить ситуацию «на фото платный декор, выбрана базовая цена». Не исправлять её догадкой о доплате. Неотождествлённые кадры не делать отдельным выбором до подтверждения; составить короткий список только таких ID. Не требовать пересъёмку всего ассортимента.

Веб-изображения: одинаковое поле 1:1, товар целиком (`object-fit:contain`), без обрезки упаковки, заданные width/height; первая видимая строка сразу, ниже lazy. Оригиналы не перезаписывать; использовать имеющиеся WebP/оптимизированные копии, не тонировать фото под кремовый фон.

## 6. Точные тексты: верх, низ, карточка товара
**Верх каталога:** логотип + «Дели Берри», звонок и корзина со счётчиком. H1 «Клубника в шоколаде». Подзаголовок «Наборы и букеты — для подарка и для себя». Строка «Самовывоз или курьерская доставка». Далее категория, размер, тип, оформления. Не добавлять сверху длинный рассказ о процессе и повторную кнопку «Выбрать подарок».

**Подписи:** свежая — «Свежая клубника в шоколаде»; сублимированная — «Хрустящая сублимированная клубника в шоколаде». Готовность отдельно: «Приготовим за 20–30 минут» / «Приготовим за 30–60 минут» / «В наличии» согласно SKU. Не писать одновременно «приготовим» и «в наличии» для одного выбранного товара. Не использовать общее «от 20 минут» для наборов и букетов.

**Низ каталога:** «Заберите заказ в удобной точке»; «Discovery и Zеленопарк · 10:00–22:00»; «Цены одинаковые в обеих точках»; действие «Адреса и маршруты». Помощь: «Нужна помощь с выбором?» + телефон. Ссылки «Контакты», «О продавце», «Условия заказа», «Персональные данные». Нижнее меню «Каталог / Мои заказы / Контакты», корзина в шапке. Использовать существующие страницы, не создавать дубли роутов.

**Товар:** назад → выбранное фото/галерея → название и количество → тип/готовность → оформление → разрешённые дополнения → итог. Выбор фото не теряется при открытии подробностей. Если несколько ценовых вариантов, читаемые строки/миниатюры, не три узкие колонки на телефоне. Заголовок «Букет из N ягод», под ним выбранная упаковка из матрицы; без кодов.

|Изделие|Описание|
|---|---|
|9 / 16 ягод|«N ягод клубники в шоколаде в подарочной коробке».|
|12 ягод|«12 ягод клубники в шоколаде». Для свежей: «Можно выбрать ягодное оформление».|
|25 ягод|«25 свежих ягод клубники в шоколаде в крафтовой коробке».|
|C02|«12 ягод клубники и 2 банана в шоколаде». Бейджи «Ассорти», «12 + 2»; не «14 ягод».|
|Букет|«N ягод клубники в шоколаде». Далее реальная упаковка выбранного оформления.|

Блоки «Состав и аллергены», «Упаковка», «Хранение» — только подтверждённые сведения. Не выдумывать вес, порции, шоколад определённой марки, ручную работу, пользу, отсутствие аллергенов. Недостающая маркировка — локальный контентный блокер перед продажей, а не скрываемый пробел.

Удалить «подтверждённое оформление A06», «карточка и фотография сохранены», «Цена меняется вместе с выбранным типом клубники», неподтверждённые «Популярный/Хит» и ложный дефицит. «Пример оформления» оставлять только там, где необходимо честно раскрыть отличие.

CTA товара: **«В корзину · {сумма} ₽»**. После добавления «Товар в корзине» + «Перейти в корзину», без принудительного перехода. Под суммой «Курьерская доставка оплачивается отдельно». Не добавлять товар молча значком «+». До подтверждения серверного расчёта не выдавать предварительную сумму за окончательную.

## 7. Корзина, получение и время
Корзина хранит SKU, оформление, тип, дополнения/надпись, количество и сумму. Объединять только полностью одинаковые конфигурации; одинаковые SKU с разным оформлением/надписью — разные строки. Разрешить изменить/удалить и «Добавить ещё». После изменения цены на сервере показать новую сумму для явного согласия, не подменять незаметно. Выбор группы не меняет сохранённые строки.

Заголовок шага **«Оформление заказа»**. Сначала **«Как получить заказ?» → «Самовывоз / Курьерская доставка»**. Точка приготовления выбирается для обоих способов. В карточке точки — адрес/режим и отдельная ссылка на карту, не ссылка вместо выбора.

Самовывоз: «Где и когда заберёте?», точка, дата и время. Доставка: адрес, имя/телефон получателя, «Желаемое время доставки». Можно использовать данные покупателя без повторного ввода. Курьер — сторонний сервис за счёт клиента, координирует единый оператор после готовности. Не обещать минуту прибытия или мгновенный расчёт тарифа. До оплаты товара ясно: тариф доставки оплачивается отдельно. Оператор согласует тариф до вызова; дополнительный платёж/вызов не автоматизировать без реального подключённого процесса.

Контактные поля: имя, «Телефон для связи по заказу», адрес только для доставки, «Комментарий — необязательно». Под комментарием: «Пожелания проверит оператор. Изменения состава и цены согласуем до оплаты». Постоянные labels, обязательные отмечены; ошибка текстом рядом с полем. Не добавлять обязательные дату рождения/email; контакт для кассового чека — по фактической кассовой схеме. Согласия не отмечать заранее и не объединять с рекламной подпиской.

**Время:** любой будущий день и сегодня при возможности; 10:00–22:00, шаг **15 минут** в UI/API/данных, включая исправление старого `slotMinutes:30`. Дата в итогах по-русски, время 24-часовое, расчёт в `Europe/Moscow`; хранение времени с однозначным часовым поясом. Не ставить произвольный горизонт 7/30 дней.

Свежий набор 20–30 минут, свежий букет 30–60, сублимированный в наличии. Для ближайшего получения сегодня сервер учитывает минимум 30/60 минут, округляет вперёд к доступному слоту; для предзаказа допускается 10:00. Многотоварную нагрузку и точное время подтверждает оператор: ни сумма, ни максимум нормативов не являются автоматической гарантией изготовления партии. Доставка дополнительно требует времени пути. Клиенту **никогда** не выводить «заказать до 21:00/21:30»; недоступные интервалы не предлагать. Перед подтверждением и созданием оплаты повторно проверить срок/точку/стоп-лист.

|Получение|Итог|
|---|---|
|Самовывоз|«Товары — {сумма} ₽»; «Самовывоз — бесплатно»; «Итого — {сумма} ₽».|
|Курьер|«Товары — {сумма} ₽»; «Доставка — оплачивается отдельно»; «К оплате за товары — {сумма} ₽».|

Не писать «Доставка — 0 ₽», когда тариф неизвестен. Под временем: «Время подтвердит оператор». Перед CTA: **«Оператор проверит заказ и свяжется с вами. Оплата — после подтверждения»**. CTA **«Отправить заказ на подтверждение»**. Срок резерва неоплаченной заявки, штрафы и правила возврата по догадке не вводить.

## 8. Заказы, ошибки, один оператор
Успех только после надёжного сохранения на backend: **«Заказ №{номер} получен» / «Ожидает подтверждения оператора»**. Показать комплектацию, сумму, точку/получение, телефон и «Мои заказы». Это не подтверждение времени оператором и не оплата.

При потере ответа: «Не удалось подтвердить отправку. Повторим проверку без создания второго заказа». Корзину/форму не очищать до подтверждённого результата. Повторять с тем же idempotency key; БД и транзакционная запись должны предотвращать дубли даже при конкурентных запросах. Не объявлять «не создан», если сервер мог сохранить заявку.

Пустая корзина: «Корзина пока пуста» + «Выбрать набор или букет». Пустая история: «Здесь появятся ваши заказы» + «Открыть каталог». Без входа: «Откройте приложение в Telegram, чтобы увидеть свои заказы» — не пустая история. Стоп-лист: «Этот вариант временно недоступен» + допустимые альтернативы. Ошибка загрузки: «Не удалось загрузить каталог» + «Повторить» + телефон, не «товаров нет».

Один оператор видит все заказы обеих точек: номер, время, точка, способ получения, покупатель/получатель, фото выбранного оформления, состав, дополнения, сумма, оплата, история. Действия: проверить/подтвердить, согласовать изменение, создать/повторно отправить платёжную ссылку, передать точке, отметить изготовление/готовность/выдачу/передачу курьеру, обработать отмену/возврат, аварийный стоп-лист по точке. Кнопка копирования передачи включает всю комплектацию и номер. Не создавать роли отдельных сотрудников или сложную CRM.

Минимальный путь: `WAITING_CONFIRMATION → CONFIRMED → PAYMENT_PENDING → PAID → SENT_TO_STORE → IN_PRODUCTION → READY → COMPLETED`; доставка после готовности: `COURIER_ORDERED → COURIER_PICKED_UP → DELIVERED`. Дополнительно `CANCELLED`, `REFUND_PENDING`, `REFUNDED`, `EXPIRED_UNCLAIMED`. Сохранить совместимость существующих кодов, при необходимости использовать отображение статусов, а не ломать историю. Платёжный статус и стадия исполнения не должны перезаписывать друг друга.

Каждый переход проверяется сервером и журналируется: время, действующий пользователь/провайдер, старое/новое состояние, причина. Покупатель видит только свои заказы и понятные русские статусы. Оператор не может вручную поставить «Оплачен»/«Возвращён»; действие «запросить возврат» не равно подтверждённому возврату. Поздний платёж по отменённому/просроченному заказу — операторское исключение, не автоматический запуск производства.

Уведомления: оператору новый заказ/оплата/ошибка/отмена; покупателю получение заявки, подтверждение, ссылка оплаты, оплата, готовность, передача курьеру, завершение/отмена. В сообщении номер и единый контакт. Сбой Telegram не теряет заказ: сохранять задачу уведомления и статус доставки, повторять безопасно; ошибка видна оператору. Отказ покупателя от сообщений не блокирует просмотр статусов. Не рассылать непрошенные рекламные сообщения.

## 9. Хранение и документы
Правила лично утверждены владельцем; это не новое технологическое заключение:
- Свежие изделия: до **24 часов с изготовления при +2…+6 °C**, закрытая упаковка; желательно употребить в день получения; не замораживать.
- Сублимированные: до **3 месяцев с изготовления** в закрытой упаковке, сухое место, **18±3 °C**, влажность ≤75%; фактическая дата — по маркировке партии, не от покупки.
- Неявка: держать заказ до суток после назначенного получения, **но никогда дольше срока годности**. Клиентский текст: «Храним заказ на точке до 24 часов, но не дольше срока годности».

Оператор фиксирует фактическое `manufactured_at`; для свежего сервер вычисляет `expires_at=manufactured_at+24h`, а `hold_until=min(назначенное получение+24h, expires_at)`. Не считать срок от создания заявки или оплаты. Для смешанного заказа учитывать самое раннее истечение по позициям; партия сублимированного — по маркировке. По истечении блокировать выдачу/передачу курьеру, уведомлять оператора; не продлевать срок простым редактированием и не признавать оплату автоматически потерянной. Правила отмены/возврата согласовать по реальной схеме, не придумывать.

Страницы «О продавце», «Условия заказа», «Персональные данные», контакт, карты открываются с телефона. Реквизиты из §1, регистрационный адрес отдельно от самовывоза. Состав/аллергены — по техкарте, не по чужому магазину. До сбора реальных контактов подтвердить применимость схемы хранения/обработки персональных данных и необходимые правовые тексты; бесплатность хостинга этого не доказывает. До закрытия такого блокера допустимы публичная витрина без приёма персональных данных и синтетический тестовый контур; не переносить реальные контакты в новое зарубежное хранилище автоматически.

## 10. Яндекс Пэй и защита
Яндекс Пэй уже выбран; не заменять его другим провайдером и не требовать повторного подключения организации, если оно существует. До доступа подготовить интеграцию, но не изображать рабочую оплату. Кнопка **«Оплатить через Яндекс Пэй»** доступна после подтверждения заказа оператором и реальной готовности интеграции.

Backend создаёт платёж по сохранённому заказу и серверной сумме, сохраняет идентификатор провайдера и ссылку. Не более одного активного платёжного сценария и одного успешного списания на подтверждённую версию заказа. При повторе запроса использовать тот же ключ; при истекшей ссылке сначала проверить существующий платёж. После выставления оплаты нельзя менять состав/цену незаметно: новая согласованная версия и безопасное закрытие предыдущего сценария.

Открывать полученный разрешённый HTTPS paymentUrl по действию пользователя штатным способом Telegram/браузера, не самодельной формой карты и не iframe. После возврата — **«Проверяем оплату»** и чтение статуса с backend. Redirect, скриншот, кнопка и frontend не устанавливают `PAID` [TG].

Webhook Пэй: `POST /v1/webhook`, сырое тело `application/octet-stream`, JWT **ES256**, проверка публичными JWKS нужной среды, `kid`, допустимого алгоритма, времени и `merchantId` [YP1]. Не придумывать `YANDEX_PAY_WEBHOOK_SECRET` вместо подписи. Callback Base URL — без повторного `/v1/webhook`. `PAID` только после валидного события **CAPTURED**, связанного с правильным заказом. Сумму/валюту сверять с сохранённым платежом и ответом API: не ждать полей суммы в каждом webhook. Повторы дедуплицировать по смыслу события/операции, не хешу JWT — повтор может содержать новый JWT. Не откатывать оплаченный/возвращённый статус старым событием [YP2].

Возврат и чек — по существующей кассе/налогообложению продавца; не выдумывать ставку НДС и не считать кнопку доказательством фискализации. Проверить sandbox, включая отказ/отмену/повтор/возврат. Нет реквизитов — `NOT TESTED`, а не «оплата готова». Боевой режим/реальный платёж требуют отдельного разрешения.

Telegram: backend проверяет подпись `initData` и срок `auth_date`; не доверяет `initDataUnsafe` или Telegram ID из формы. Затем allowlist одного оператора, проверка принадлежности каждого заказа покупателю [TG]. Токен бота и ключ Пэй только в секретах среды; отдельные тест/production, HTTPS, rate limit, серверная валидация, ограничения уникальности, параметризованные запросы. Не отдавать персональные API в публичный кеш/статические файлы; не логировать токены/initData, полные телефоны и адреса. Черновики не хранить бессрочно, очищать после подтверждённой отправки. Персональные данные и ключи не включать в скриншоты/репозиторий/отчёт.

Базовое согласованное направление — **Cloudflare Workers Free + D1 + Static Assets**. Продолжать уже подготовленную ветку; не возвращаться к платному Render/PostgreSQL/Vercel и не начинать новый выбор платформ. Если фактически уже работает другое согласованное размещение, сохранить его до фиксации необходимых изменений, а не мигрировать ради CSS.

Использовать уже настроенные имена секретов/переменных, не плодить аналоги: Telegram bot token и operator ID; Yandex Merchant ID/API key/среда/callback; параметры текущего deployment. Не удалять backend, нужный старым незавершённым платежам/заказам; старый checkout выключить, историю сохранить. Миграцию входов отделить от включения боевой оплаты.

Для Telegram использовать существующую авторизацию. Если её нет и доступен бесплатный браузер: открыть `https://web.telegram.org/k/`, показать действующий QR Telegram именно этой сессии или ссылку на живое окно, дождаться входа. Не генерировать QR входа, не подменять его QR ссылки на бота, не запрашивать пароли/коды в чате. Если бесплатного способа нет, сразу один конкретный блокер, без платных запусков и повторного направления на неработающую настройку.
